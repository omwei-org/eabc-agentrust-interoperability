## OS-09 — Missing L7 metadata and credential-injection boundary

**Evidence class:** `SOURCE` + `TEST-CONTRACT`. **Status: NOT TESTED — behavior for credentialed endpoints with missing L7 metadata requires an end-to-end check.**

At the pinned baseline, compatibility tests explicitly preserve an L4-only fallback when authorized L7 metadata is missing, including an absent route snapshot and default TLS/allowlist/exact-host values ([compatibility tests, lines 282–307](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/proxy/tests/compatibility.rs#L282-L307)). A separate test asserts that an authoritative policy evaluation error denies rather than using that fallback ([lines 309 onward](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/proxy/tests/compatibility.rs#L309-L325)). The proxy also queries a separate credential-provenance guard before materializing the L7 route ([proxy, lines 2757–2775](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/proxy.rs#L2757-L2775); [credential guard query, lines 1029–1059](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/opa.rs#L1029-L1059)).

The fallback is not by itself proof of a defect: L4-only endpoints may be intentionally supported, and the separate credential guard may preserve relevant restrictions. The source-level compatibility test does not, by itself, demonstrate that a credentialed endpoint can never receive injected credentials when L7 metadata is missing or malformed. That must be established across the full decision → credential guard → route materialization → upstream request path.

**EABC relevance:** `NON_BYPASSABILITY(B,E)` requires that the protected effect cannot escape the intended authorization boundary through a fallback path; `INTEGRITY_CTX(C,B,E)` requires the endpoint/credential context used for injection to match the authorization decision. Where credentials are injected, the protected effect is the upstream request carrying those credentials.

**Verification plan:** configure a credentialed endpoint that requires L7 constraints; separately simulate absent L7 metadata, missing credential-guard metadata, malformed metadata, and authoritative evaluation error. Use an upstream canary that records headers/body and whether any injected credential arrived. Verify no credential is injected and no protected request reaches the canary unless the intended endpoint/credential binding and policy are established. Include wildcard hosts, aliases, redirects if supported, and policy reload during the request. Runtime status remains `NOT TESTED`.

## BASELINE-04 — Delegated backend assurance boundary

**Evidence class:** `SOURCE` + `TEST-CONTRACT`. **Status: NOT TESTED — trust in the admitted delegated implementation remains an operator/deployment assurance question.**

The source does **more than simply accept an arbitrary payload**. The supervisor selects a backend from trusted composition, requires a matching admitted backend name before decoding, then binds the decoded sandbox ID, session and runtime generation to trusted launch inputs ([`SelectedBackend::select`, lines 51–140](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor/src/backend_setup.rs#L51-L140)). The registration tests reject unknown or differently cased names, mismatched backend/TLS/fence/identity inputs, and mismatched admission before decode/discovery ([registration tests, lines 37–109](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor/src/backend_setup/tests.rs#L37-L109); [admission rejection test, lines 387–416](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor/src/backend_setup/tests.rs#L387-L416)). The common runtime also checks that the confirmation matches generation, session, identity, resource claims and provisioning-evidence digest ([runtime confirmation, lines 357–375](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-sandbox-backend/src/runtime.rs#L357-L375)).

At the same time, the delegated-backend contract intentionally allows `backend_audit = null` and then starts the agent ([delegated test, lines 81–107](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-sandbox-backend/src/runtime/tests/delegated.rs#L81-L107)). The shared startup contract states that backend selection is made by trusted composition, not payload contents. These controls establish admission and context binding; they do **not alone demonstrate the truth of the admitted backend's enforcement claims**. This is not automatically a vulnerability: it may be the intended trust boundary for an operator-selected external backend.

**EABC relevance:** `NON_BYPASSABILITY(B,E)` and `INTEGRITY_DEF(B)` require evidence that the admitted backend's actual boundary is complete and enforced; `INTEGRITY_CTX(C,B,E)` requires the enforcement state to correspond to the admitted identity, generation and protected effect. A matching descriptor/evidence digest proves binding of the value, not the truth of the backend's enforcement assertion.

**Verification plan:** document the admission and operator trust model for every enabled backend; verify how the registered endpoint is authenticated and protected against process/socket replacement; enumerate backend versions and configuration; test a deliberately non-enforcing but correctly admitted backend in an isolated harness and determine whether the gateway has any independent signal to detect that mismatch; and observe protected effects at the destination. Keep the null-`backend_audit` behavior as an explicit protocol contract, not a failure by itself. Runtime status remains `NOT TESTED`.

## BASELINE-03 — VM outer-fence evidence and launch binding

**Evidence class:** `SOURCE`. **Status: NOT TESTED — source supports no-NIC-by-construction; runtime binding not independently verified.**

At the checked upstream commit, `VmOuterFenceEvidence::project` rejects an empty generation or non-zero network-device count. `VmBoundarySpec::provision` sets `network_device_count: 0` as a fixed value ([VM isolation contract, lines 22–42 and 71–94](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-vm/src/isolation/mod.rs#L22-L42)). Further source review found relevant counter-evidence: the QEMU launch arguments explicitly include `-nic none` ([QEMU launch and network arguments, lines 121–150 and 188–190](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-vm/src/runtime.rs#L121-L150)); the libkrun path states that it starts no network helper and uses the protected vsock mapping plus optional virtiofs shares, disables implicit vsock, and explicitly adds only vsock/virtiofs devices ([libkrun launch, lines 320–354](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-vm/src/runtime.rs#L320-L354)). A source unit test asserts QEMU's `-nic none` arguments ([lines 908–911](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-vm/src/runtime.rs#L908-L911)).

This is meaningful source-level support for a no-IP-NIC-by-construction design, so the fixed zero count is not by itself evidence of a defect. The remaining assurance gap is that the count is not derived from a measured final device inventory, and neither these source assertions nor the evidence digest proves the effective runtime configuration under every supported platform, launcher version, or failure/recovery path. Vsock is a host/guest communication channel and should be assessed as part of the boundary; it is not an ordinary guest IP NIC.

**EABC relevance:** `INTEGRITY_DEF(B)` asks whether the boundary definition is complete and stable; `INTEGRITY_CTX(C,B,E)` asks whether the declared generation/context corresponds to the actual enforcement instance; `NON_BYPASSABILITY(B,E)` requires evidence that all paths to the protected effect traverse the boundary. A generation-bound digest alone does not prove the effective VM device configuration, although the reviewed launch code provides relevant supporting evidence.

**Verification plan:** on each supported QEMU/libkrun platform, capture the effective device configuration and host-side network state; verify no NIC or alternate direct-egress helper exists; inspect vsock endpoint exposure and policy; exercise restart/recovery and launcher failure; where feasible, inject an unexpected device and require launch/confirmation to fail closed. Record exact VM backend, host platform, launcher and libkrun/QEMU versions and evidence artifacts. Runtime status remains `NOT TESTED`.

## BASELINE-02 — Outer-fence assurance contract changed

**Evidence class:** `SOURCE`. **Status: NOT TESTED — assurance-contract change, runtime effect unknown.** This is a concrete source-level difference between the pinned audit baseline and the checked newer upstream commit. It is not, by itself, proof of a runtime vulnerability.

At the pinned baseline, `OuterFenceGuarantees::validate` required the exact set `DefaultDenyEgress`, `NoUnmanagedEgressPath`, `RevocationVerified`, and `ControllerLossFailsClosed` for the admitted generation ([old contract, lines 389–469](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-isolation-interface/src/contract.rs#L389-L469)). At the checked newer upstream commit, this common guarantee set is replaced by `ProvisioningEvidence`, which binds native evidence to a generation and explicitly says the digest is not independent proof of policy enforcement ([new contract, lines 219–293](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-isolation-interface/src/contract.rs#L219-L293)). The Docker projection itself checks non-empty container ID, `network_mode == "none"`, and no unexpected networks before creating the evidence digest ([Docker isolation, lines 25–60](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-docker/src/isolation.rs#L25-L60)). Importantly, Docker also inspects the actual container configuration and attached networks and rejects drift ([Docker outer-fence inspection, lines 3082–3110](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-docker/src/lib.rs#L3082-L3110)). Podman likewise inspects the actual container and rejects a non-`none` network mode, privileged mode, or attached network ([Podman fence verification, lines 564–595](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-podman/src/client.rs#L564-L595)); its launch and restart paths call this check before starting the workload ([launch path, lines 1536–1546](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-podman/src/driver.rs#L1536-L1546), [restart path, lines 1636–1644](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-driver-podman/src/driver.rs#L1636-L1644)). The common runtime validates generation, session, resource claims and evidence-digest equality before proceeding, and validates native audit schema only for its built-in backend ([runtime confirmation, lines 357–389](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-sandbox-backend/src/runtime.rs#L357-L389)). A delegated-backend test intentionally accepts `backend_audit = null` and proceeds to `start_agent` ([delegated runtime test, lines 81–101](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-sandbox-backend/src/runtime/tests/delegated.rs#L81-L101)).

**Interpretation:** the newer design may deliberately move enforcement-specific validation into trusted driver/backend code. Therefore, the removal of common normalized guarantees is not enough to claim a regression. But the old common interface's explicit four-property check is no longer present at this layer. We need evidence showing where each equivalent guarantee is now established, validated, and maintained through runtime failure and policy change.

**EABC relevance:** `NON_BYPASSABILITY(B,E)` requires evidence that all paths to the protected effect traverse enforcement; `INTEGRITY_STATE(B,E)` requires evidence for revocation and controller-loss transitions where applicable; `INTEGRITY_CTX(C,B,E)` requires binding of the admitted generation/session/identity/policy to the actual enforcement state. An evidence digest binds bytes to a generation; it does not itself prove the truth or completeness of the claims represented by those bytes.

**Falsification / verification plan:** for Docker, Podman and VM independently, inspect the trusted native validation path and test default-deny, attempted unmanaged egress, revocation of previously allowed traffic, and controller/broker loss. Use an upstream canary that records whether any protected bytes arrive. Include built-in and delegated backends, including missing, empty, malformed and semantically incomplete audit evidence. Record whether launch is refused and whether active traffic is closed; do not treat digest equality or successful startup alone as proof.

## OS-06 — Authorization generation / credential guard

**Evidence classes:** `SOURCE`, `TEST-CONTRACT`; RFC statements are `DOC-CLAIM`. **Runtime status: NOT TESTED — race behavior not validated end-to-end.**

**EABC relevance:** `INTEGRITY_STATE(B,E)` and `INTEGRITY_CTX(C,B,E)` because policy generation and endpoint context must remain bound to the decision; `NON_BYPASSABILITY(B,E)` if a stale decision can reach the protected effect. These are audit mappings, not conformance conclusions.

The original audit baseline is pinned to `a4c848adbddd0b4732fd70ddcf8a563a5b1e9317`. A follow-up source-drift review at `b58e24c9dabd6d4bcf2b7186592d3ad50646541b` found explicit generation guards around CONNECT setup, upstream dialing, the CONNECT success response, and active relays. The guard captures an expected generation, rejects a mismatch when created, exposes `ensure_current()`, and waits for generation changes; CONNECT code rejects a stale route before dialing, races upstream dialing against a stale-generation signal, and checks the guard again before sending `200 Connection Established` ([generation guard, lines 206–249](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor-network/src/opa.rs#L206-L249); [CONNECT checks, lines 2947–2999](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor-network/src/proxy.rs#L2947-L2999)). A source unit test reloads policy and asserts a stale forward relay writes no bytes to upstream ([test, lines 14100–14150](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/crates/openshell-supervisor-network/src/proxy.rs#L14100-L14150)).

**Unresolved documentation/implementation discrepancy:** RFC 0005 `current-shape.md` still describes separate metadata queries not all asserted against the L4 generation ([lines 221–240](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/rfc/0005-sandbox-proxy-egress-adapter/current-shape.md#L221-L240)), while its implementation plan calls for a single generation-consistent authorization result and reload-race tests ([lines 66–83](https://github.com/NVIDIA/OpenShell/blob/b58e24c9dabd6d4bcf2b7186592d3ad50646541b/rfc/0005-sandbox-proxy-egress-adapter/implementation-plan.md#L66-L83)). The source guards materially mitigate stale-generation use at the dial/relay boundary, but do not alone prove that every materialized field came from the same generation or that all race windows are covered. Record this as an unresolved documentation/implementation discrepancy until the maintainers reconcile the RFC appendix with the exact implementation and its tests; do not label it a confirmed vulnerability.

The separate credential-guard query does not itself return a generation. That fact alone is not a vulnerability because the surrounding guards may reject stale decisions. The relevant falsification test must observe the actual protected effect, not just supervisor logs.

**Falsification test:** add barriers between primary authorization, credential-guard query, TLS/L7 metadata hydration, final generation check, upstream dial completion, and CONNECT success. Reload from a raw-tunnel-allowed rule to a credentialed endpoint requiring L7, and reverse. During active HTTP/raw relays, publish both a valid new generation and a fail-closed quarantine generation. Use an upstream canary that records request bytes and whether injected credentials arrived. Expected fail-closed result: no stale-generation protected bytes or credentials reach upstream; a stale CONNECT is rejected before success, and active stale relays close. Runtime status remains `NOT TESTED`.

## OS-07 — Evaluation error vs missing L7 metadata

**Evidence class:** `TEST-CONTRACT` (source regression tests inspected). **Runtime status: NOT TESTED — source regression contract only.**

**EABC relevance:** `INTEGRITY_CTX(C,B,E)` and `NON_BYPASSABILITY(B,E)`: a fallback must not silently weaken the boundary applicable to the protected effect.

Pinned test file: [`compatibility.rs`, lines 283–330](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/proxy/tests/compatibility.rs#L283-L330).

Tests cover missing authorized L7 metadata falling back to L4-only defaults and an authoritative evaluation error denying rather than falling back. This is a useful distinction, but it does not prove every production retrieval/decode failure follows the same fail-closed path. More importantly, the L4-only fallback itself needs risk assessment for endpoints using credential injection: determine whether the weaker L4 decision can still permit a protected request or expose injected credentials when L7 metadata is missing. [Pinned compatibility tests, lines 270–345](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-supervisor-network/src/proxy/tests/compatibility.rs#L270-L345).

## OS-08 — VM bind mounts / virtiofs

**Evidence classes:** `DOC-CLAIM`, `SOURCE`, and `TEST-CONTRACT`. **Runtime status: NOT TESTED — host-path escape status unknown.**

**EABC relevance:** `NON_BYPASSABILITY(B,E)` and `INTEGRITY_DEF(B)` for the filesystem boundary; `INTEGRITY_CTX(C,B,E)` where the configured share defines the authorized context.

Pinned source areas: `crates/openshell-driver-vm/src/driver.rs`, `scripts/openshell-vm-sandbox-init.sh`, `src/ffi.rs`, `README.md`, and `e2e/rust/tests/vm_bind_mount.rs`.

- Bind mounts are opt-in (`enable_bind_mounts` defaults false) and rejected when resource admission is enabled.
- Mount configuration has `read_only` defaulting true; the flag is passed to the libkrun virtiofs API.
- Source path validation checks absolute paths, rejects a final symlink, checks directory/accessibility at provisioning, and fails on missing/inaccessible paths.
- Guest target validation rejects reserved/internal paths and overlaps; guest init refuses symlink target components and fails if mount fails.
- E2E test contract covers two temporary host shares, read/write behavior for RW, and refusal to overwrite through RO.
- OpenShell VM README warns host bind mounts expose host files and may bypass workspace isolation/filesystem policy.

Upstream libkrun documentation warns that virtiofs alone does not isolate a share from other directories/filesystems visible to the host VMM process and recommends host OS mount isolation. This is a material question, not proof that OpenShell is vulnerable: inspect the actual launch environment and verify whether the VMM process is restricted to the intended host paths. Test with harmless canary files outside the allowed share, separately for RO/RW and each supported host platform. Also test symlinks and hardlinks inside the shared tree that target outside paths, `..` traversal, and already-open file descriptors; determine whether the host VMM process or guest can follow those paths. [VM read-only default, lines 140–160](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-driver-vm/src/driver.rs#L140-L160); [bind-mount opt-in and validation, lines 5150–5165](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-driver-vm/src/driver.rs#L5150-L5165); [guest virtiofs target checks, lines 526–585](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/crates/openshell-driver-vm/scripts/openshell-vm-sandbox-init.sh#L526-L585); [VM bind-mount E2E test, lines 1–100](https://github.com/NVIDIA/OpenShell/blob/a4c848adbddd0b4732fd70ddcf8a563a5b1e9317/e2e/rust/tests/vm_bind_mount.rs#L1-L100).
